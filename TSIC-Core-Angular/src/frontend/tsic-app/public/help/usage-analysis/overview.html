Usage Analysis

How the platform is actually being used — every API request, by event, over a window you choose. This is the drill behind the Usage by Event dashboard widget: the widget shows the glance, this page lets you take it apart.

Scope

The Scope dropdown decides which events the numbers cover. What you can pick depends on your role:

  • This event — the event you are signed into. A Director sees only this; the dropdown is replaced by a label.
  • Customer — every live event belonging to the same customer as this one. SuperDirector and above.
  • All TSIC — every live event on the platform. Superuser only.
Live events only.

Every scope covers events whose registration window is still open. A concluded event never appears here, and if the event you are standing in has concluded, the page says so instead of showing an empty chart.

Window and bots

  • 24h / 7d / 30d — the time window every report covers.
  • Bucket — stands in for Window while a report that shows change through time is on screen. Daily covers the last 30 days, Weekly the last 12 weeks, Monthly the last 12 months; the bucket is the window, so the two are never picked separately.
  • Event — shown at Customer and All TSIC scope: narrows every report to one live event in the scope, or All events for the whole set. A Director has one event and never sees it.
  • Client — narrows every report to one app: the web app, TSIC Teams or TSIC Events. Only clients that actually have activity in the current selection are offered; if the one you chose drops out, the choice returns to All clients. Requests from a build that does not identify itself count under All clients and cannot be picked out.
  • What is counted at all — only requests from TSIC's own apps, driven by people. A request with no recognisable app tag, or from a caller that announces itself as a crawler or a script, is never recorded here. Usage analysis describes how clients use the system, not how machines interrogate it.

Reading it well

  • The banner under the controls states exactly what the numbers on screen were fetched with — scope, how many live events that is, and the window or bucket. Hover the event count to see which events.
  • Counts are API requests, not page views. One screen in the app may make several.
  • Anonymous means the request carried no signed-in user — public schedules, rosters and event browsing. It is not a count of distinct visitors; nothing in the data can identify one.

Reports

Pick a report from the Report dropdown. Each is one question about the same scope and window. Reports are being added as the questions are settled; a report that shows only its name and the query it would run is a slot not yet filled in.

The dropdown groups reports by who they are about. Signed-in users covers every request made by someone logged in, whether or not they had a registration at the time. Public (not signed in) covers every request made with no one logged in. Every request belongs to exactly one of the two.

Signed-in users
  • Users by Role — how many people used the event, counted by registration and grouped by role, every role by its own name, Directors included. One column per role for the event picked in the Event dropdown, or the whole scope rolled up at All events; the table beneath lists every event with a Total, an All row on top where All is a choice. A registration is per event, so a user in two events counts in each. A family account working through player registration has no registration of its own yet, so it is not counted here; User Requests by Route shows that activity. Public visitors who never sign in are not people this data can count — what they asked for is Public Requests by Route.
  • Users by Role over Time — Users by Role asked once per day, week or month, so the answer is a series instead of a number: one line per role in the same colours, plus a heavier Total line, every line on the same baseline. The newest point is hollow: the current bucket, still filling. A gap in a line is a bucket from before the log began, which is unknown rather than zero. The table beneath lists every bucket, newest first. A user counts in every bucket they were active in, so the buckets do not add up to Users by Role's total for the span: that report is distinct over the whole span, this one is distinct per slice. An event counts only in the buckets it was live in, so this report also covers events that concluded during the span, in the buckets before they concluded; the chart title says how many events that is.
  • User Requests by Route — what signed-in people did: their requests per event, grouped by the API route they hit, with failed requests (4xx / 5xx) counted apart. The Role dropdown narrows the report to one role, so a Director's work is not buried under families registering. Role is the one the person was registered under. A family account going through player registration has no registration yet and shows as Family; any other login without a registration (usually an adult self-registering) shows as No registration. Beside the request count is the number of people who made them — counted by registration, or by login where there was none — and hovering a bar shows it per route, so a route used heavily by one person reads differently from one used by hundreds.
Public (not signed in)
  • Public Requests by Route — what the public asked for without signing in: anonymous requests per event, grouped by the API route they hit, with failed requests (4xx / 5xx) counted apart so scanners and stale links never inflate the routes the public came for. Requests, not people: nothing in the log can turn an anonymous request into a visitor. Routes are the API endpoint, not the page, so one page fires several.
