Manual ARB Sweep — FAQ

A dry run proves what the sweep would do. It cannot prove the emails are well written.

Wrong wording renders perfectly. Read the message bodies as a parent would, not just the counts.

Why does my button say “Dry run”? Where is the switch to make it send?

There isn't one, by design. The mode follows the server: production sends, every other server renders. A switch would be one more thing that can be left in the wrong position, and the wrong position on production is severe — a whole morning's payments not booked, while the run still reports success. Making it impossible to ask for is safer than making it easy to get right.

I ran a dry run and no email arrived. Is it broken?

No — that is the whole point. Nothing is transmitted off production, including the digest and the expiring-card summary. Everything that would have been sent is on the screen instead: expand any row under “Family emails” to read the exact message, and scroll down for the digest.

Then is a dry run looking at fake data?

No. It reads the real production Authorize.Net batches — the same transactions the 4 AM pass would see — and resolves each one against real registrations, real families and real balances. It is a read-only look at live data. Only the writing and the sending are withheld.

This matters because the alternative was worse than useless: before, an off-production run quietly queried the Authorize.Net test account, found nothing, and reported a clean morning — indistinguishable from a real clean morning, and from a broken sweep.

What are the [DRY RUN] rows in the Email Log?

A dry run still records what it would have sent, so you can review it in the Email Log the same way you review any other batch. Those rows are prefixed [DRY RUN] precisely so nobody — you, a director, or a parent looking at their own sent-mail list — ever mistakes a rendered message for one that actually went out.

They only exist on non-production servers, and that database is a restored copy, so they disappear at the next refresh from production.

Why is there one log entry per job instead of one per family?

Same as any batch email sent from Search Registrations: one entry per job, per message type, listing every recipient with a count. A morning where one job had both a live-plan failure and a dead-plan failure produces two entries for that job, because those are two different messages.

Looking up a single family still works exactly as before — their address is matched inside the recipient list, so the family's record and their own sent-mail view both find it.

The log entry shows !PLAYER and !OWEDNOW instead of real names. Is that a bug?

No. A batch entry stores the message template, not any one family's copy — the same as every other batch email in the system. Each family's actual email is personalised with their player, their username and their balance, so no single stored copy could represent the batch, and picking one family's to stand in for everyone else's would be misleading.

To read the finished, personalised messages, use the dry run on this screen — it shows every one of them in full.

Why are eCheck Settled, eCheck Returns and Orphans missing from a dry-run result?

Because those steps genuinely do not run. They exist to move or reverse money, and none of them affects the failed-draft notices this screen is for. Skipping them entirely is safer than teaching each one a “don't write” mode — code that never runs cannot write by mistake.

They are hidden rather than shown as zeros, because a zero next to “eCheck Returns” reads as “nothing bounced last night”, and on a dry run that would be a claim nobody checked.

One of the emails says Reply-To “none”. What does that mean?

No director with an email address could be found for that job, so a family replying to the notice would reach TSIC support instead of their own club. Worth fixing at the source — give that job an active director with a valid address — because the family is replying about their own money.

If I run the sweep twice, do families get emailed twice?

No. A transaction that has already been imported is recognised and skipped before it ever reaches the notification step, so a second run the same morning writes to nobody. The dry run inherits the same behaviour.

A family whose card fails again on the next installment is a new failed transaction, and does get a new notice. That is intended — it is a new failure.

Some families are listed as NOT emailed. Why weren't they just sent something?

Because the email would not have worked. The four reasons: no sendable address on the account; no family username, so the sign-in instructions would be blank; the registrant has opted out of email; or the send itself failed. A notice telling someone to sign in as nothing produces a support call, not a payment.

They are named on screen and in the digest so a person can pick them up by phone. That list is the real output of the run.

Why can't I trigger the expiring-card pass on production?

It writes to thousands of families across every job with a live subscription, and it is scheduled on the 2nd and the 15th exactly so that sending it is not a decision anyone makes. A button on production would add only one capability: sending it a second time, or on the wrong day, with no way to take it back.

Use the dry run here to see who is in scope and what they would receive. The pass itself stays on its timer.

How many days prior should I use?

1 unless you have a reason. That matches what runs nightly. Widen it to review a window you think was missed, or after an outage. Nothing is double-counted — already-processed transactions are skipped — so a bigger number costs time, not accuracy.

It says “Sweep already running”.

Only one pass may run at a time, and a second request is refused rather than queued — two passes at once could each decide the same transaction was unbooked and book it twice. Wait for the first to finish and run again.

The banner says the mode could not be determined.

The server did not answer when asked which mode it runs in. Do not click until you know — on production that button sends real mail to real families. Reload the page; if it persists, the API is likely down or unreachable, which is worth resolving before running a reconciliation pass anyway.
