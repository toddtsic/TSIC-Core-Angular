### AR-029: [Reporting / Excel export] A bare single-column result set steals the header row — "Tournament Keys — ALL" exports with NO column headings
- **Topic**: SP-Excel export path (`ReportingService.BuildExcelFromSheets` feed) → any proc emitting a single-column result set before its data. Reported against **Tournament Keys — ALL**.
- **Observation (Ann, 08-24)**: re-ran the report after AR-014 was applied — *"No headings and I don't see tournament start and end dates."* Screenshot: **row 1 blank, row 2 `2026`, row 3+ data with nothing labelled**, columns A–V.
- **✅ ROOT-CAUSED (Claude, 08-24) — one bug explains BOTH complaints, and it is in the EXPORTER, not the proc.**
  - **The dates were never missing.** `reporting.[TournamentKeyAttributes-ALL]` selects them properly aliased as **`EventStart` / `EventEnd`** (proc lines 29-30, 99-100) — **columns B and C**, immediately after `jobName`. Ann cannot identify them because there is no header row to read.
  - **The proc emits FOUR result sets**: `'QA Test: ' + @qaTest` (sheet name) · `convert(varchar, @thisYear)` (a bare year) · then the two data selects.
  - **The exporter mishandles the middle one** (`ReportingService.cs:944-980`). The `FieldCount == 1` branch consumes one row and only calls `NextResultAsync()` when the value starts with `"QA Test:"`. The bare year does **not** match, so execution falls through into the row loop, which fires `rowCounter == 0 && current.Columns.Count == 0` and registers **that** result set's column name — **unnamed, therefore blank** — as the sheet's one and only column, then writes `2026` as row 1 of the data.
